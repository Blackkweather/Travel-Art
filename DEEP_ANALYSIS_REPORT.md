# Travel Art — Deep Analysis Report

**Date:** 28 July 2026
**Scope:** Full codebase audit (backend, frontend, deployment, repository hygiene)

> This report replaces the previous version dated 31 December 2024, which scored
> Security 20/20 "Perfect" and concluded "No Critical Issues Found". That
> assessment was wrong: at the time it was written, the repository publicly
> exposed a user data export and a live database password, and shipped an
> unauthenticated endpoint that allowed account takeover. The old report appears
> to have been generated by pattern-matching filenames — it credited CSRF and
> input-sanitisation middleware that were never imported anywhere.

---

## Critical findings

### 1. User data export committed to a public repository
`users_export.csv` contained real user emails, bcrypt password hashes, phone
numbers, and internal IDs.

**Status:** removed from the working tree. **Still present in git history.**

### 2. Live database password hardcoded in source
`backend/src/db.ts` carried a Supabase project reference and password as a
fallback value.

**Status:** removed from the working tree. **Still present in git history — the
password must be rotated.**

### 3. Unauthenticated account-takeover endpoint
`POST /api/auth/clerk/sync` required no authentication and accepted an
attacker-supplied `clerkId`, `email`, and `role`. Posting the email address of
an existing user attached the attacker's Clerk identity to that account; the
auth middleware would then accept the attacker's token as that user.

Clerk had already been removed from the frontend, but the backend routes stayed
mounted, so the endpoint was reachable with no corresponding legitimate caller.

**Status:** fixed — route deleted along with the Clerk auth branch.

### 4. Forgeable tokens when `JWT_SECRET` was unset
`config.ts` fell back to the literal `'fallback-secret-key'`. Any environment
missing the variable signed and accepted tokens under a value published in the
repository, allowing anyone to mint a token for any user ID and role.

**Status:** fixed — production now fails to start unless a secret of at least 32
characters is set.

### 5. CORS allowed every origin with credentials enabled
`index.ts` built an allowlist, then called `callback(null, true)`
unconditionally, so the allowlist had no effect. Combined with
`credentials: true`, any website could issue authenticated cross-origin
requests on behalf of a logged-in user.

**Status:** fixed — explicit allowlist, with an optional regex for Vercel
preview URLs.

## Repository hygiene

- **`.gitignore` ignored `prisma/migrations/`.** Migrations were tracked only
  because they were added before the rule. A fresh clone could have shipped
  without them, breaking `prisma migrate deploy`. Fixed.
- **`.gitignore` ignored `public`,** excluding frontend public assets. Fixed.
- **`devcpp-4.9.9.2_setup.exe`** — a 9.3 MB installer for a 2005-era C++ IDE,
  committed to the repository. Removed.
- **`backend/prisma/dev.db.backup`** and a nested stray
  `backend/prisma/backend/prisma/dev.db-journal` — database files in version
  control. Removed.
- **Self-referential dependency.** Both `backend` and `frontend` declared
  `"travel-art": "file:.."`, depending on the repository root. Nothing imported
  it. Removed.
- **Dead middleware.** `middleware/csrf.ts` and `middleware/sanitize.ts` were
  never imported. Removed rather than wired up — the sanitiser stripped quotes
  and angle brackets from every request field, which would have silently
  corrupted passwords and legitimate text. Zod validation and Prisma's
  parameterised queries already cover the relevant risks.
- **Orphaned microservices.** `services/` holds eight Express services
  (`api-gateway`, `auth-service`, `booking-service`, and others) referenced by
  no code, no `package.json`, and no deployment config. Left in place but
  excluded from deployment. **Recommend deleting** unless there is a migration
  plan.

## Not verified

- **Test suite.** All 9 backend suites fail locally with
  `PrismaClientInitializationError` — they are integration tests requiring a
  reachable PostgreSQL instance and there is no local one. The suites were not
  run against a live database as part of this audit, so the code changes above
  are verified by typecheck and build only.
- **Dependency vulnerabilities.** `npm audit` reported 19 issues (1 critical, 14
  high) for the backend. Not investigated.
- **Frontend.** Audited only for Clerk remnants and build health. No systematic
  review of the React application was performed.

---

## Actions still required

1. **Rotate the Supabase database password.** It is in public git history and
   removing the file does not revoke it.
2. **Treat the exported user data as breached.** Emails, phone numbers, and
   bcrypt hashes were public. Consider forcing a password reset and check
   whether disclosure obligations apply.
3. **Purge both from git history** (`git filter-repo`) and force-push. Deferred
   by request — until then, the data remains retrievable from any clone.
4. **Set the remaining production environment variables:** `DATABASE_URL`,
   `BLOB_READ_WRITE_TOKEN`, `CORS_ORIGIN`, `FRONTEND_URL`.
5. **Run migrations as a release step:** `npm --prefix backend run prisma:deploy`.
